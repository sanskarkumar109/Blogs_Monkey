### Architectural Trade-offs Q&A

#### 1. Why Django & Django ORM instead of Node.js or FastAPI?
- **Interview Answer**: "Django provides an battle-tested 'batteries-included' foundation with an integrated ORM, security middleware (CSRF, XSS headers, clickjacking), session management, and admin interface out of the box. This allowed me to focus on business logic and security hardening rather than writing boilerplate authentication or ORM mappings."
- **Deep Technical Rationale**: Django's ORM abstracts database dialect differences while offering query optimization tools (`select_related`, `prefetch_related`, `only`, `defer`). Its built-in migration engine guarantees schema version control aligned with git commits.

#### 2. Why MySQL 8.0 instead of PostgreSQL or MongoDB?
- **Interview Answer**: "MySQL 8.0 is widely supported across hosting providers, highly optimized for read-heavy transactional workloads, and supports modern JSON data types and full-text indexing. For a SaaS blogging platform where read queries (blog viewing) outnumber write queries (drafting/editing) by orders of magnitude, MySQL 8.0 provides exceptional throughput with InnoDB's row-level locking."
- **Why not MongoDB?**: "Blogging platforms have relational domain entities—users, profiles, posts, categories, tags, comments, likes, bookmarks. Document stores like MongoDB require manual denormalization or lack ACID multi-document transactions across relational boundaries."

#### 3. Why Django Templates + HTMX instead of React/Vue SPA?
- **Interview Answer**: "For a content-heavy SaaS where SEO, fast initial load times (First Contentful Paint), and low architectural complexity are paramount, server-side rendering with Django templates is ideal. By pairing Django templates with HTMX and Alpine.js, I achieved SPA-like interactivity (instant like toggles, search autocomplete, modal forms) without client-side hydration overhead, duplication of routing logic, or managing separate frontend state."

### Database Optimization & Query Execution Strategy

#### N+1 Query Elimination in `blog/views.py`
**Problem**: Fetching 10 blogs and rendering their author name, author profile avatar, category name, and list of tags would trigger 1 + 10 (author) + 10 (profile) + 10 (category) + 10 (tags) = **41 SQL queries**.

**My Solution**:
```python
queryset = Blog.objects.filter(status='PUBLISHED')\
    .select_related('author', 'author__profile', 'category')\
    .prefetch_related('tags')
```
- `select_related`: Performs a SQL `INNER JOIN` / `LEFT OUTER JOIN` on single-valued foreign keys (`author`, `category`) in a **single query**.
- `prefetch_related`: Performs a secondary query using SQL `IN (...)` for multi-valued relationships (`tags`) and joins the objects in Python memory, preventing N+1 queries across many-to-many joins.

## PHASE 5 — DJANGO DEEP DIVE & CORE MECHANICS

### Django Architecture (MVT)

```text
         [ Model ] ◄──(Data definition & ORM queries)──┐
            ▲                                         │
            │                                         ▼
[ Request ] ┴──► [ View ] (Business Logic) ──► [ Template ] ──► [ Response ]
```

### Key Internal Mechanics Explored in Project

1. **Lazy QuerySets**: `Blog.objects.filter(status='PUBLISHED')` does NOT execute a database query when defined. Evaluation is deferred until the QuerySet is iterated over (e.g., in a `for` loop in template rendering), sliced, or explicitly evaluated with `list()`, `len()`, or `exists()`.
2. **Custom Middleware**: Processing flows top-to-bottom on request, bottom-to-top on response. Used in our stack for security header enforcement (`SecurityMiddleware`), session resolution (`SessionMiddleware`), and CSRF token verification (`CsrfViewMiddleware`).
3. **Context Processors**: `content.context_processors.site_settings` injects global site metadata into every rendered template context automatically, avoiding the need to manually pass site settings in every view.

## PHASE 6 — AUTHENTICATION & AUTHORIZATION AUDIT

### IDOR (Insecure Direct Object Reference) Prevention

#### Vulnerability Scenario:
A malicious user logs in as `User A` and navigates to `/dashboard/blogs/15/edit/`. They change the URL to `/dashboard/blogs/16/edit/`, where Blog 16 belongs to `User B`.

#### My Project's Defense Mechanism (`apps/dashboard/views.py`):
```python
class BlogUpdateView(LoginRequiredMixin, View):
    def get(self, request, pk):
        blog = get_object_or_404(Blog, pk=pk)
        
        # Explicit Ownership Check
        if blog.author != request.user and not request.user.is_staff:
            raise PermissionDenied("You cannot edit another user's post.")
            
        form = BlogForm(instance=blog)
        return render(request, 'dashboard/blog_form.html', {'form': form, 'blog': blog})
```
- **Result**: Django intercepts `PermissionDenied` and immediately renders a `403 Forbidden` response (`403.html`), blocking unauthorized mutation or viewing.

### State Machine Lifecycle

```text
[ Author Creates Post ] ──► Status: DRAFT
                               │
                       (Author Edits & Saves)
                               │
                       (Author Clicks "Submit for Review")
                               ▼
                    Status: PENDING_REVIEW
                               │
            ┌──────────────────┴──────────────────┐
     (Admin Approves)                      (Admin Rejects)
            ▼                                     ▼
   Status: PUBLISHED                     Status: REJECTED
            │                                     │
   (Author Archives)                     (Author Edits & Resubmits)
            ▼                                     ▼
   Status: ARCHIVED                      Status: PENDING_REVIEW
```

### Workflow Integrity Controls
- **Author Permissions**: Normal users can only transition their posts from `DRAFT` to `PENDING_REVIEW` or `ARCHIVED`.
- **Admin Permissions**: Only users with `request.user.is_staff == True` can transition posts to `PUBLISHED` or `REJECTED`. Any attempt by an author to send `status='PUBLISHED'` directly in form POST data is stripped and overridden by the form/view save logic.

## PHASE 9 — PERFORMANCE & SCALABILITY ROADMAP

### Scaling Strategy from 1,000 to 1,000,000 Users

1. **Caching Tier (Redis)**:
   - Cache rendered blog detail HTML pages or JSON API payloads using Redis (`django-redis`).
   - Invalidate cache entries on blog edit/update.
2. **Database Optimization & Read Replicas**:
   - Primary MySQL instance handles writes (`DRAFT`, `COMMENT`, `LIKE`).
   - Read replicas handle read-heavy traffic (`home`, `blog_detail`, `search`).
3. **Asynchronous Background Processing (Celery + Redis)**:
   - Offload transactional emails (welcome emails, password resets, review notifications) to Celery workers.
   - Defer image resizing/compression to background jobs.
4. **Media CDN & Object Storage**:
   - Migrate local `/media/` folder to Amazon S3 or Cloudflare R2 served over Cloudflare CDN.

## PHASE 15 — RAPID-FIRE QUESTIONS (1–3 SENTENCE ANSWERS)

1. **What is ORM?** An Object-Relational Mapper that maps database tables to Python classes, allowing developers to query and manipulate data using Python code instead of SQL.
2. **What is Middleware?** A framework of hooks into Django’s request/response processing that executes custom logic globally before requests hit views or after views return responses.
3. **What is CSRF?** Cross-Site Request Forgery, an attack that tricks a logged-in browser into submitting unauthorized requests; prevented using secret tokens validated on POST requests.
4. **What is XSS?** Cross-Site Scripting, an attack injecting malicious JavaScript into web pages; prevented in our app via `nh3` HTML sanitization and Django template auto-escaping.
5. **What is `select_related`?** A QuerySet optimization that performs SQL `JOIN`s to fetch single-valued foreign key relationships in a single query.
6. **What is `prefetch_related`?** A QuerySet optimization that performs additional queries to prefetch multi-valued or many-to-many relationships using SQL `IN` clauses.
7. **What is WSGI?** Web Server Gateway Interface, a standard specification defining how Python applications communicate with web servers like Gunicorn or Nginx.
8. **What is Gunicorn?** A pre-fork worker WSGI HTTP server for UNIX that executes Python Django applications concurrently under production loads.
9. **What is Nginx?** A high-performance HTTP server and reverse proxy used to handle TLS/SSL, serve static/media files directly, and forward app requests to Gunicorn.
10. **What is an Index in MySQL?** A B-Tree data structure created on database columns to accelerate row lookup operations at the expense of slight write overhead.

### Scenario 1: A user alters a URL parameter from `/dashboard/blogs/15/edit/` to `/dashboard/blogs/16/edit/` to access another user's post. What happens?
- **Response**: The view queries `Blog` by `pk=16`. Before rendering or updating, the view compares `blog.author` with `request.user`. Because they do not match and `request.user.is_staff` is False, the view raises `PermissionDenied`. Django catches this and returns an HTTP 403 Forbidden response.

- **Response**: I would check slow query logs, verify index utilization on `status` and `published_at`, wrap post detail views in Redis caching using `django-redis`, and implement read replicas for SELECT queries.

## PHASE 17 — ACTUAL PROJECT CHALLENGES & SOLUTIONS

1. **PyMySQL Windows Compatibility**: MySQL C-extensions can fail to compile on Windows. **Solution**: Configured `pymysql.install_as_MySQLdb()` in `config/__init__.py` to ensure smooth execution across OS platforms.
2. **HTML Sanitization Links (`nh3`)**: Standard sanitizers strip attributes aggressively. **Solution**: Configured `nh3.clean()` with custom tag and attribute permissions while preserving anchor links without security compromise.
3. **Dual Login Authentication**: Standard Django authentication expects a username. **Solution**: Overrode `UserLoginForm.clean()` to resolve input strings matching user email addresses back to their associated username prior to invoking `authenticate()`.
